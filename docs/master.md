# Cómo se aplica el máster

Qué parte de IncidApp demuestra cada módulo del *Máster de Desarrollo con IA*, con un enlace a la evidencia dentro de este repositorio. Todos los enlaces son relativos y se comprueban con el comando del final.

| Módulo | Qué se aplica | Evidencia |
|---|---|---|
| **M1 · Ingeniería de software** | Requisitos funcionales y no funcionales con ID y prioridad MoSCoW, historias de usuario, actores y empresa ficticia. Matriz de permisos como especificación de la autorización. Diagramas UML: **máquina de estados**, **capas de la API** (componentes), niveles de atomic design y una secuencia de cambio de estado. Glosario español ↔ inglés | [requisitos.md](requisitos.md) · [permisos.md](permisos.md) · [diagramas.md § estados](diagramas.md#1--máquina-de-estados-de-una-incidencia-diagrama-de-estados) · [diagramas.md § capas](diagramas.md#2--capas-de-la-api-diagrama-de-componentes) · [glosario.md](glosario.md) |
| **M2 · Arquitectura de software** | Monolito modular con **Clean Architecture** en la API (`domain` ← `application` ← `infrastructure`/`http` ← `composition`), comprobada con ESLint y con un test. Contrato compartido con Zod en `packages/shared`. **Atomic design** en la web (tokens → átomos → moléculas → organismos → plantillas → páginas), también comprobado con ESLint. 9 ADR | [ADR](adr/README.md) · [ADR-002](adr/002-clean-architecture.md) · [ADR-008](adr/008-atomic-design-storybook.md) · [eslint.config.js](../eslint.config.js) · [architecture.test.ts (API)](../apps/api/src/architecture.test.ts) · [architecture.test.ts (web)](../apps/web/src/components/architecture.test.ts) · [packages/shared/src](../packages/shared/src/index.ts) · [composition root](../apps/api/src/composition/container.ts) |
| **M3 · Fundamentos de la IA** | Uso consciente de los modelos: contexto mínimo y explícito para cada agente (cada subagente lee la spec y la tarea, no el razonamiento del principal), **revisores con contexto limpio** para evitar el sesgo de confirmación, modelo más ligero para las revisiones y la QA, y verificación humana en los puntos de control (spec, plan, UI). Límites de la IA documentados: un hallazgo que solo aparece al compilar, no en los tests | [harness.md](proceso-ia/harness.md) · [hallazgos-revisores.md](proceso-ia/hallazgos-revisores.md) · [flujo.md](proceso-ia/flujo.md) |
| **M4 · Herramientas** | Claude Code como agente principal con subagentes, *skills*, *hooks* y permisos; `gh` para PR y CI; Git con ramas por feature, *worktrees* para trabajar en paralelo y *squash merge*. Husky, lint-staged y commitlint en cada commit. Revisiones automáticas (`code-reviewer` y `security-reviewer`) en cada tarea | [harness.md](proceso-ia/harness.md) · [commitlint.config.js](../commitlint.config.js) · [.lintstagedrc.json](../.lintstagedrc.json) · [.husky/commit-msg](../.husky/commit-msg) · [hallazgos-revisores.md](proceso-ia/hallazgos-revisores.md) |
| **M5 · Flujo de desarrollo con IA** | Un agente principal que actúa de *tech lead*: elige la tarea, delega en el subagente que indica `tasks.md`, verifica, lanza los revisores, corrige y hace commit con el ID de la tarea. *Harness* propio (instrucciones del proyecto, subagentes, *skills*, *hooks* y reglas) que se describe sin publicarse | [flujo.md](proceso-ia/flujo.md) · [harness.md](proceso-ia/harness.md) · [metricas.md](proceso-ia/metricas.md) |
| **M6 · Calidad** | TDD en dominio y casos de uso; tests de API con `fastify.inject` y **matriz completa de autorización**; Testing Library en la web; E2E con Playwright de los flujos principales (`e2e/`, [T-07.02](specs/F07-entrega/tasks.md)). **Storybook en local** (`npm run storybook`) con el addon de accesibilidad: cada átomo, molécula y organismo tiene su *story*. CI en GitHub Actions (lint, tipos, tests y build) en cada PR; Render solo despliega con la CI en verde | [authorization-matrix.test.ts](../apps/api/src/http/authorization-matrix.test.ts) · [authorization-policy.test.ts](../apps/api/src/application/authorization/authorization-policy.test.ts) · [status-machine.test.ts](../apps/api/src/domain/incidents/status-machine.test.ts) · [ci.yml](../.github/workflows/ci.yml) · [Storybook (.storybook/main.ts)](../apps/web/.storybook/main.ts) · [tokens](../apps/web/src/styles/tokens.css) · [metricas.md](proceso-ia/metricas.md) |
| **M7 · Infraestructura y cloud** | Despliegue con **coste cero**: un *web service* gratuito de **Render** (Node nativo; la API sirve también el front compilado) y PostgreSQL gratuito en **Neon**. Infraestructura como código en `render.yaml`, con migraciones y *seed* al arrancar (el plan gratuito no tiene *pre-deploy*). PGlite en local y en tests (sin Docker). **Docker queda como trabajo futuro** (decisión 4 de F07) | [render.yaml](../render.yaml) · [ADR-006](adr/006-despliegue-coste-cero.md) · [ADR-004](adr/004-pglite-local-neon-produccion.md) · [.env.example](../.env.example) · [requisitos.md § Trabajo futuro](requisitos.md#trabajo-futuro) |
| **M8 · Seguridad** | OWASP Top 10: autorización decidida solo en el servidor (`AuthorizationPolicy`, 404 si no es visible y 403 si no está permitido) y `allowedActions` en las respuestas; contraseñas con argon2id; sesión en BD con cookie `httpOnly`, `secure` y `sameSite=Lax`, rotada al iniciar sesión; anti-CSRF con `X-Requested-With`; *rate limit* del login; CSP con Helmet; validación con Zod; historial y auditoría solo de inserción; bloqueo `FOR UPDATE` contra condiciones de carrera. Revisión de seguridad por un agente en cada tarea sensible | [ADR-003](adr/003-sesion-en-bd.md) · [ADR-009](adr/009-permisos-en-servidor.md) · [authorization-policy.ts](../apps/api/src/application/authorization/authorization-policy.ts) · [argon2-password-hasher.ts](../apps/api/src/infrastructure/auth/argon2-password-hasher.ts) · [csrf.ts](../apps/api/src/http/csrf.ts) · [session-cookie.ts](../apps/api/src/http/auth/session-cookie.ts) · [hallazgos-revisores.md](proceso-ia/hallazgos-revisores.md) |
| **M9 · Desarrollo potenciado por IA** | **Spec-Driven Development**: cada feature tiene `spec.md` (criterios de aceptación `CA-xx.y`), `plan.md` y `tasks.md` (tareas `T-xx.yy` con agente, dependencias, paralelismo y verificación); nada se implementa fuera de una tarea, y cada commit cita su tarea (RF → CA → T → commit → PR).
